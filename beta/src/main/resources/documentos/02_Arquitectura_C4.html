1. Vista general

Objetivo del documento: describir la arquitectura de Facimus Procesos (Beta) en los cuatro niveles del modelo C4 (contexto, contenedores, componentes y código) y justificar las decisiones que la sostienen.

Principales decisiones arquitectónicas:

  • Aplicación de una sola página (Angular) y API REST sin estado con JWT.
  • Monolito modular en Spring Boot, organizado por dominio: gestion, modelado, security y common.
  • Multiempresa con una sola base de datos y la columna empresa_id en cada entidad (EntidadEmpresa y RepositorioTenant).
  • Eliminación lógica explícita, un repositorio por servicio y orquestadores para las operaciones transaccionales.
  • Contenedores Docker en VMs, con nginx como proxy del mismo origen y despliegue continuo.

Tecnologías y versiones utilizadas: Angular 20.3, TypeScript 5.9, nginx 1.27; Java 21, Spring Boot 4.1 (Spring Security, Spring Data JPA, Hibernate 7.4, Bean Validation), JJWT 0.12.6, ModelMapper 3.2, springdoc-openapi 3.0; PostgreSQL 18.6 (H2 2.4 en desarrollo); Docker 29.10, GHCR, GitHub Actions, SonarCloud y Tailscale.

2. Nivel 1 - Contexto

Actores externos: administrador de empresa, editor, lector (solo lectura) y usuarios de empresas invitadas a procesos compartidos; también el visitante sin sesión, que solo puede registrar una empresa o aceptar una invitación.

Sistemas externos: sistemas de la empresa que recibirían los mensajes del proceso (servicio web o correo): el modelo registra su destino, pero esta versión no los invoca. Tailscale Funnel publica la aplicación por HTTPS. GitHub, GHCR y SonarCloud solo intervienen en la construcción y el despliegue.

Descripción de interacciones: todos los usuarios usan la aplicación desde el navegador por HTTPS. El administrador registra la empresa y gestiona usuarios, roles, permisos y procesos compartidos; el editor modela y publica; el lector y los usuarios invitados consultan. Cada petición viaja con un JWT y el sistema solo devuelve datos de la empresa del usuario o de procesos compartidos con ella.

3. Nivel 2 - Contenedores

Aplicación frontend: SPA en Angular 20 con componentes standalone y rutas diferidas; authGuard y rolGuard protegen las rutas; los interceptores agregan el JWT y renuevan la sesión ante un 401. Se compila a archivos estáticos que sirve nginx 1.27 en el contenedor beta-front (128 MB, con /healthz); nginx reenvía /api al backend, de modo que el navegador habla con un solo origen.

Servicios / backend: API REST en Spring Boot 4.1 sobre Java 21 y Tomcat 11, en el contenedor beta-back (perfil prod, 1 GB). Expone /api/v1 con 16 controladores, sin estado (JWT) y con errores en formato ProblemDetail. La documentación OpenAPI existe en desarrollo y está apagada en producción.

Persistencia y almacenamiento: PostgreSQL 18.6 en una VM dedicada (base proyecto_desarrollo). Hibernate 7.4 valida el esquema al arrancar (ddl-auto=validate); cada tabla lleva empresa_id y las entidades eliminables, la columna activo. En desarrollo y en las pruebas de integración se usa H2.

Integraciones: Tailscale Funnel (HTTPS público hacia beta-front), GHCR (imágenes), GitHub Actions (CI/CD por Tailscale y SSH) y SonarCloud (análisis estático). Los destinos externos de los mensajes solo se registran.

4. Nivel 3 - Componentes

Contenedor seleccionado: API REST (backend Spring Boot).

Componentes internos y responsabilidades:

  • Seguridad: JwtAuthenticationFilter valida el token, recarga el usuario y arma el principal (usuario, empresa y rol); SecurityConfig define las reglas por ruta y rol, CORS y la política sin sesión.
  • Controladores de gestión y de modelado: contrato REST, validación de entrada (@Valid) y mapeo a DTO.
  • Servicios y orquestadores: reglas de negocio por entidad; EmpresaOrquestador, ProcesoOrquestador, PoolOrquestador y CorrelacionOrquestador coordinan operaciones transaccionales; ValidacionModeloService revisa el modelo antes de publicar.
  • Repositorios: Spring Data JPA sobre RepositorioTenant, con consultas filtradas por empresaId y activo.
  • Transversales: ModelMapperConfig (entidad a DTO), ApiExceptionHandler (ProblemDetail) y eventos de dominio (publicación del proceso y pool de caja negra).

Relaciones y dependencias: cada petición recorre filtro → controlador → servicio u orquestador → repositorio → PostgreSQL. Los servicios de modelado consultan a los de gestión para comprobar que el proceso esté activo y que el rol tenga el permiso de estructura. Cada servicio inyecta solo su propio repositorio, regla que verifica ArchUnit (SeparacionRepositoriosTest, 15 casos).

5. Nivel 4 - Código (opcional)

Módulo o componente seleccionado: modelo de dominio del modelado BPMN (paquetes modelado.model y gestion.model).

Diagrama o estructura de clases / módulos: todas las entidades extienden EntidadEmpresa (@MappedSuperclass con empresa_id obligatorio e inmutable). Actividad, Gateway y EventoMensaje heredan de NodoFlujo en una sola tabla (SINGLE_TABLE, discriminador tipo_nodo), de modo que un Arco apunta a cualquier nodo con dos claves foráneas. Proceso contiene pools, cada pool lanes con un RolProceso, y cada lane nodos; Mensaje une dos pools y sus eventos THROW y CATCH, y Correlacion define el criterio del mensaje (figura 4).

6. Decisiones y atributos de calidad

Seguridad y control de acceso: JWT HS256 con access token de 15 min y refresh token de 7 días; reglas por ruta y rol (ADMINISTRADOR, EDITOR, SOLO_LECTURA); permisos de estructura configurables; aislamiento por empresa en cada consulta; contraseñas con BCrypt; secretos por variables de entorno; Swagger apagado en producción. Detalle en el documento 08.

Escalabilidad y rendimiento: la API no guarda estado, así que admite varias réplicas detrás de nginx. Con 50 usuarios el p95 queda por debajo de 579 ms; la autenticación con BCrypt es el primer límite de CPU. open-in-view está desactivado y los @EntityGraph cargan las relaciones necesarias en una sola consulta.

Mantenibilidad: paquetes por dominio, un repositorio por servicio, 35 reglas de arquitectura con ArchUnit, DTO inmutables (records) con ModelMapper, errores uniformes y SonarCloud con calificación A, deuda técnica de 0 min y 89,3 % de cobertura.

Justificación de decisiones y compromisos: se eligió simplicidad operativa (un solo despliegue, una sola base y sin estado) acorde con el tamaño del equipo y el plazo. Los compromisos aceptados son: sin revocación de tokens en el servidor, aislamiento por disciplina de consulta en vez de esquemas separados (mitigado con RepositorioTenant y 47 pruebas) y columnas nulas por la herencia en una sola tabla.

Decisiones arquitectónicas

Tabla 2. Decisiones arquitectónicas.
ID Decisión Alternativa Justificación
DA-01 SPA en Angular + API REST Aplicación renderizada en el servidor (Thymeleaf) Permite el editor interactivo y pruebas separadas de front y back.
DA-02 Monolito modular en Spring Boot Microservicios Un solo despliegue y transacciones locales, acorde con el equipo y el plazo.
DA-03 Multiempresa por empresa_id Un esquema o una base por empresa Una sola base; el aislamiento se fuerza en cada consulta y se prueba con 47 casos.
DA-04 JWT sin estado (access 15 min y refresh 7 días) Sesión HTTP con cookie Escala sin estado y sin riesgo de CSRF; no permite revocar tokens en el servidor.
DA-05 Eliminación lógica con filtros explícitos @SQLDelete y @SQLRestriction Filtros visibles y auditables, sin efectos ocultos sobre el filtro de empresa.
DA-06 Herencia SINGLE_TABLE en NodoFlujo JOINED o tabla por clase Arcos con una sola clave hacia nodos_flujo y consultas simples; deja columnas nulas.
DA-07 Un repositorio por servicio y orquestadores Servicios con varios repositorios Responsabilidades claras y transacciones en un solo lugar; lo verifica ArchUnit.
DA-08 nginx como proxy del mismo origen CORS abierto en el backend El backend no queda expuesto a Internet y el navegador usa un solo origen.
DA-09 Docker y despliegue continuo a VMs Despliegue manual con mvnw y ng serve Despliegues repetibles, con aprobación y verificación automáticas.
