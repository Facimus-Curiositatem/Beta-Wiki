1. Alcance técnico

Componentes frontend cubiertos: 52 archivos de prueba (*.spec.ts) con 233 casos: 28 componentes (formularios y listas de procesos, pools, lanes, actividades, gateways, arcos, eventos, mensajes, roles, usuarios, permisos, compartir, login, registro y diagrama), 17 servicios HTTP, 2 guards (authGuard y rolGuard), 2 interceptores (auth y refresh), la configuración de rutas (h4 y h8) y el componente raíz.

Componentes backend cubiertos: 58 clases de prueba con 468 casos:

  • Servicios: gestión (10 clases, 54 casos) y modelado (12 clases, 137 casos).
  • Controladores REST: gestión (8 clases, 59 casos) y modelado (8 clases, 65 casos).
  • Seguridad: 4 clases, 101 casos (JWT, autorización por rol, aislamiento entre empresas e integración del flujo de tokens).
  • Transaccionalidad e invariantes: 8 clases, 16 casos; arquitectura (ArchUnit): 7 clases, 35 casos; arranque del contexto: 1 caso.

Frameworks de prueba y versiones:

  • Backend: JUnit Jupiter 6.0.3, Mockito 5.23.0, AssertJ 3.27.7, Spring Boot Test 4.1.0 y Spring Test 7.0.8 (MockMvc), ArchUnit 1.4.0, H2 2.4.240 y JaCoCo 0.8.13, sobre Java 21.0.13 (Temurin) y Maven.
  • Frontend: Angular 20.3, Jasmine 5.6, Karma 6.4 con Chrome sin ventana (Chrome 157), karma-coverage 2.2, karma-junit-reporter 2.0 y TypeScript 5.9.

Estrategia de mocks / fixtures:

  • Servicios (backend): @ExtendWith(MockitoExtension.class) con @Mock e @InjectMocks aíslan cada servicio de sus repositorios y de los servicios que llama; los datos se arman en @BeforeEach.
  • Controladores: @WebMvcTest y MockMvc con servicios simulados y un usuario autenticado inyectado (ApiPrincipalRequestPostProcessor y SeguridadControllersTestAutoConfiguration).
  • Integración: @SpringBootTest con H2 en memoria y una base por clase para probar seguridad, aislamiento entre empresas y transacciones reales.
  • Frontend: TestBed con provideHttpClientTesting y HttpTestingController (30 archivos), espías de Jasmine con createSpyObj (18 archivos) y datos compartidos en src/app/testing/compartidos.fixture.ts.

2. Pruebas unitarias

Criterios de selección de unidades: toda clase con reglas de negocio (validaciones BPMN, unicidad de nombres y correos, estados del proceso, eliminación lógica), cada controlador REST (contrato HTTP y códigos de respuesta), los componentes de seguridad (JwtService, filtro y autorización), las reglas de arquitectura y, en el frontend, los servicios HTTP, los guards, los interceptores y los componentes con lógica de formulario o de lista. Se priorizaron las reglas señaladas en las auditorías del curso: multiempresa, procesos inactivos y correo único.

Casos representativos: la tabla «Casos unitarios» resume 16 casos reales del backend y del frontend; los nombres corresponden a los métodos de prueba de los reportes JUnit y Karma.

Comandos para ejecutar pruebas:

  • Backend completo con cobertura: ./mvnw clean verify (reporte en target/site/jacoco/index.html).
  • Solo reglas de arquitectura: ./mvnw test -Dtest="com.facimus.procesos.arquitectura.**"; una clase: ./mvnw test -Dtest=ArcoServiceTest.
  • Frontend en CI: npx ng test --watch=false --browsers=ChromeHeadlessCI --code-coverage (reporte en coverage/beta-front/index.html); en local: ng test.

Resultados, cobertura y exclusiones justificadas:

  • Backend: 468/468 casos aprobados, 0 fallos y 0 omitidos (47,9 s). JaCoCo: líneas 94,3 % (1.725 de 1.830), ramas 72,8 %, instrucciones 92,4 % y métodos 90,4 %.
  • Frontend: 233/233 casos aprobados. Cobertura: líneas 79,1 % (865 de 1.094), sentencias 77,1 %, funciones 62,3 % y ramas 45,5 %.
  • Exclusiones: no se configuraron exclusiones de cobertura ni de análisis; las clases de bajo valor (por ejemplo, ProcesosApplication.main, con 37 %) cuentan en el total.
  • Aserciones: de los 311 métodos de prueba del backend, 310 tienen aserciones explícitas (assert, verify, andExpect o check de ArchUnit); el único sin aserción es contextLoads, que falla si el contexto de Spring no arranca. En el frontend, Karma no reporta ningún spec sin expect.

3. Configuración de SonarQube

Edición / versión / proyecto: SonarQube Cloud (SonarCloud), organización facimus-curiositatem, proyecto Facimus-Curiositatem_Beta-back («Facimus Procesos Backend», versión 0.0.1-SNAPSHOT), analizado con sonar-maven-plugin 4.0.0.4121 y el perfil integrado «Sonar way» para Java: panel del proyecto.

Integración con repositorio o CI: job «SonarCloud» del workflow CI/CD Backend: mvn -B verify sonar:sonar -Dsonar.qualitygate.wait=true con el secreto SONAR_TOKEN, en cada pull request y en cada push a main. La cobertura se lee de target/site/jacoco/jacoco.xml. El job falla si no se cumple el Quality Gate, el despliegue depende de él (needs: [docker, sonarqube]) y SonarCloud comenta cada PR con el check «SonarCloud Code Analysis».

Quality Gate definido: «Sonar way» (predeterminado), evaluado sobre el código nuevo: cobertura ≥ 80 %, líneas duplicadas ≤ 3 %, calificaciones A en confiabilidad, seguridad y mantenibilidad, y 100 % de security hotspots revisados. Periodo de código nuevo: versión anterior (previous_version), desde el 21/09/2026.

Reglas y exclusiones configuradas: perfil integrado «Sonar way» (Java), sin sonar.exclusions ni exclusiones de cobertura. Hay una incidencia aceptada: java:S4502 (protección CSRF deshabilitada) en SecurityConfig.java:49. Se justifica porque la API es stateless y se autentica con un JWT en el encabezado Authorization, sin cookies de sesión; el PR #32 limitó la exención de CSRF a /api/v1/** y /h2-console/**. El perfil también aplica las reglas sobre pruebas, entre ellas java:S2699 («las pruebas deben incluir aserciones»), java:S5863 y java:S5790; SonarCloud analiza los 60 archivos de prueba y no registra incidencias de esas reglas.

5. Acciones y conclusiones

Hallazgos prioritarios:

  • Cobertura de ramas del backend (72,8 %) por debajo de la de líneas; los paquetes más bajos son gestion.service (67,4 %), modelado.controller (50 %) y config (50 %).
  • En el frontend, ramas (45,5 %) y funciones (62,3 %); el resolver de rutas tiene 8,6 % de líneas y varias listas tienen 0 % de ramas.
  • El frontend (TypeScript) no está analizado en SonarCloud.
  • La versión del proyecto es fija (0.0.1-SNAPSHOT), así que el periodo de «código nuevo» no avanza desde el 21/09/2026.

Correcciones realizadas:

  • La vulnerabilidad S4502 detectada el 21/09/2026 se revisó: el PR #32 limitó la exención de CSRF a la API con JWT y la incidencia se marcó como aceptada en SonarCloud; desde el 15/10/2026 el proyecto reporta 0 vulnerabilidades.
  • El refactor del PR #37 (ModelMapper, un repositorio por servicio y eliminación de métodos of() sin uso en 19 DTO) dejó el Quality Gate en verde.
  • Entre el 15/10 y el 23/11/2026 se pasó de 444 a 468 pruebas y la cobertura subió de 88,8 % a 89,3 %, sin nuevos code smells ni duplicación.

Limitaciones / deuda técnica pendiente:

  • Agregar el frontend a SonarCloud (sonar-project.properties y un job en CI/CD Front que publique lcov.info).
  • Publicar sonar.projectVersion con el tag de cada release (vX.Y.Z) para que el código nuevo se mida por versión.
  • Subir la cobertura de ramas con casos para las rutas de error de los servicios y controladores.
  • Las pruebas de integración usan H2; las diferencias con PostgreSQL se cubren con Postman y JMeter contra PostgreSQL 18.6.
