1. Alcance y prerrequisitos

Ambientes disponibles (local, pruebas, producción):

  • Local: backend con ./mvnw spring-boot:run (H2 y datos de demostración) y frontend con ng serve.
  • Pruebas (CI): en cada pull request se levanta en beta-back un backend temporal con la imagen del PR contra las bases proyecto_ci (API y carga) o proyecto_ci_front (E2E), que se vacían antes y después.
  • Producción: beta-front (nginx) y beta-back (API) con PostgreSQL proyecto_desarrollo, publicado en https://beta-front.taila95c4c.ts.net.

Infraestructura requerida: tres VMs VMware con Ubuntu 22.04.5 LTS en la red de la universidad: beta-front y beta-back (4 vCPU Intel Xeon Gold 6240R a 2,40 GHz, 11,6 GiB de RAM y 68 GB de disco cada una) y la VM de base de datos con PostgreSQL 18.6. Las VMs de aplicación tienen Docker 29.10 con Compose y están unidas a una red Tailscale; el código y las imágenes viven en GitHub y GHCR.

Dependencias y versiones: imagen del backend: compilación con maven:3.9-eclipse-temurin-21 y ejecución con eclipse-temurin:21-jre (Spring Boot 4.1.0); imagen del frontend: compilación con node:22-alpine y ejecución con nginx:1.27-alpine; PostgreSQL 18.6; Docker 29.10; Tailscale.

Accesos y permisos requeridos: pertenencia a la red Tailscale (el CI usa un cliente OAuth con la etiqueta tag:ci), usuario deploy con llave SSH autorizada en las VMs, permiso packages:write para publicar en GHCR, entorno «production» de GitHub con revisores obligatorios (aprobación manual de cada despliegue) y acceso al archivo /opt/beta/.env de cada VM.

2. Configuración

Variables de entorno (sin divulgar secretos):

  • Backend (/opt/beta/.env en beta-back): BACKEND_TAG, DB_HOST, DB_PORT, DB_NAME, DB_USER, DB_PASSWORD, JWT_SECRET, CORS_ALLOWED_ORIGINS y DDL_AUTO. Opcionales: JWT_EXPIRATION_MINUTES (15) y JWT_REFRESH_DAYS (7).
  • Fijas en compose.yml: SPRING_PROFILES_ACTIVE=prod y JAVA_TOOL_OPTIONS=-XX:MaxRAMPercentage=70.
  • Frontend (/opt/beta/.env en beta-front): FRONT_TAG, BACKEND_URL y HTTP_BIND.

Configuración de base de datos: PostgreSQL 18.6 en su propia VM: base proyecto_desarrollo para producción y bases proyecto_ci y proyecto_ci_front para las pruebas del CI. El perfil prod usa ddl-auto=validate (Hibernate solo verifica que el esquema coincida con las entidades) y open-in-view=false.

Configuración de frontend y backend:

  • Backend: perfil prod (application-prod.properties) con PostgreSQL, consola H2 y Swagger apagados, límite de 1 GB y heap del 70 %; healthcheck TCP en el puerto 8080, publicado solo en la red de la universidad.
  • Frontend: plantilla nginx (default.conf.template) en la que ${BACKEND_URL} se reemplaza al arrancar; escucha en 8080, expone /healthz, reenvía /api/ al backend, cachea los recursos estáticos y devuelve index.html para las rutas de Angular; la SPA llama a /api/v1 en el mismo origen.

Manejo de secretos: los secretos del CI (DB_PASSWORD, DEPLOY_SSH_KEY, TS_OAUTH_CLIENT_ID, TS_OAUTH_SECRET, SONAR_TOKEN y los known_hosts) se guardan como GitHub Secrets. En las VMs viven en /opt/beta/.env con permisos 600 y nunca se suben al repositorio (solo .env.example). JWT_SECRET se genera con openssl rand -hex 32. Las credenciales temporales del CI se escriben con umask 077 y se borran al terminar, y la sesión de GHCR se cierra después de cada despliegue.

3. Procedimiento de despliegue

Preparación del entorno: una sola vez por VM: instalar Docker con el plugin de Compose y Tailscale, crear /opt/beta, copiar .env.example a .env y completarlo (chmod 600), autorizar la llave del usuario deploy y dejar libre el puerto 8080. En beta-front, publicar nginx por HTTPS con Tailscale Funnel.

Construcción / empaquetado: Dockerfiles multi-etapa: el backend se compila con Maven y corre como usuario no root (appuser); el frontend se compila con Node 22 y lo sirve nginx con HEALTHCHECK. En cada merge a main el CI publica las etiquetas :sha-xxxxxxx y :latest (en los PR, :pr-N). Al subir un tag vX.Y.Z, el workflow de release reetiqueta como :X.Y.Z la misma imagen ya probada, sin reconstruirla, y crea la release con el JAR.

Ejecución de migraciones: no se usa Flyway ni Liquibase. El esquema se crea arrancando el backend con DDL_AUTO=create sobre una base vacía y en operación normal se usa validate. Los cambios de tipo de columna se aplicaron con los scripts sql/V1__migrar_descripcion_oid_a_text.sql y sql/V2__migrar_contenido_mensaje_oid_a_text.sql (OID → TEXT), ejecutados con psql antes de reiniciar la aplicación. En el CI, cada corrida usa ddl-auto=create sobre una base vaciada.

Despliegue de componentes: el job «Desplegar» (después de la imagen y de SonarCloud en el back, o de las pruebas E2E en el front) espera la aprobación en el entorno production, se conecta por Tailscale y SSH, verifica /opt/beta/.env y que el puerto 8080 esté libre, copia deploy/compose.yml, fija BACKEND_TAG o FRONT_TAG en la etiqueta :sha-xxxxxxx del commit y ejecuta docker compose pull && docker compose up -d --wait. Al final cierra la sesión de GHCR y limpia las imágenes sin uso (docker image prune -f).

Verificación posterior al despliegue: el workflow comprueba la URL pública: en el back, que /api/v1/procesos responda 401 o 403; en el front, que /healthz responda 200 y /api/v1/procesos 401 o 403 (recorrido completo Funnel → nginx → API). Además, Compose espera a que los healthchecks de los contenedores estén sanos (--wait).

4. Operación y recuperación

Comandos de inicio, parada y reinicio: en /opt/beta de cada VM: docker compose up -d --wait, docker compose stop, docker compose restart, docker compose ps y docker compose logs -f --tail 100 backend (o front). Para actualizar: docker compose pull && docker compose up -d --wait.

Registros y monitoreo: Spring Boot y nginx escriben en la salida estándar del contenedor (docker compose logs); los healthchecks aparecen en docker compose ps; la política restart: unless-stopped reinicia los contenedores; los resúmenes del CI quedan en cada ejecución de GitHub Actions. No hay monitoreo centralizado (pendiente).

Estrategia de reversión (rollback): las imágenes son inmutables por commit (:sha-xxxxxxx) y por versión (:X.Y.Z). Para volver atrás se fija en /opt/beta/.env la etiqueta anterior (BACKEND_TAG o FRONT_TAG) y se ejecuta docker compose pull && docker compose up -d --wait, o se re-ejecuta el job de despliegue de la ejecución anterior de main. Con ddl-auto=validate, el backend no arranca si el esquema no coincide.

Respaldo y recuperación: no hay respaldo automático de la base (pendiente). Procedimiento propuesto: pg_dump -Fc proyecto_desarrollo diario en la VM de base de datos y restauración con pg_restore. La eliminación lógica y el historial de cambios permiten recuperar datos borrados desde la aplicación.

Problemas conocidos:

  • Si otro proceso ocupa el puerto 8080 (por ejemplo, un backend viejo levantado con mvnw), el despliegue se detiene con un mensaje.
  • Si falta /opt/beta/.env o el secreto DB_PASSWORD está vacío, el job falla y explica qué crear.
  • Cambiar JWT_SECRET invalida todas las sesiones abiertas.
  • Si la suite E2E falla, el front no se despliega (comportamiento esperado, como el 23/11/2026).
