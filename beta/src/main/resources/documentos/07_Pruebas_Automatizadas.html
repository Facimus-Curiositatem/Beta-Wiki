1. Objetivo y estrategia

Procesos del modelador BPMN a automatizar: los flujos completos del visor y editor de procesos: inicio y cierre de sesión con rutas protegidas, registro de empresa, ciclo de vida del proceso (BORRADOR → PUBLICADO → inactivo), modelado (pool, lane con rol, actividad, gateway y arco), y administración de usuarios y roles. Por API se automatiza el recorrido encadenado de las 28 historias, hasta la publicación y los permisos por rol.

Tipos de pruebas: UI, API, integración, extremo a extremo:

  • Extremo a extremo (UI): Selenium con pytest, 23 casos.
  • API: Newman con dos colecciones Postman (122 peticiones y 116 aserciones).
  • Integración: @SpringBootTest con H2 (seguridad, aislamiento y transacciones), dentro de los 468 casos JUnit.
  • Unitarias: JUnit con Mockito (backend) y Karma con Jasmine (233 casos en el frontend).
  • Carga: cuatro planes JMeter (documento 04); arquitectura: ArchUnit (35 casos); smoke: la imagen del front sirve /healthz, el index y las rutas de Angular; post-despliegue: verificación por la URL pública.

Herramientas y versiones: Selenium 4.53.0 con Python 3.12.16, pytest 9.2.0 y pytest-html 4.2.0 sobre Chrome sin ventana; Newman con newman-reporter-htmlextra (Node 22); Apache JMeter 5.6.3; JUnit Jupiter 6.0.3, Mockito 5.23.0 y ArchUnit 1.4.0; Karma 6.4 y Jasmine 5.6; GitHub Actions con dorny/test-reporter; Tailscale para llegar a las VMs.

2. Diseño de suites

Estructura de archivos y suites: carpeta e2e/ de Beta-front:

  • pages/: 12 Page Objects (base, login, registro, menú principal, procesos, pools, lanes, actividades, gateways, arcos, usuarios y roles). Solo ahí van los selectores.
  • tests/: 6 archivos con los escenarios (test_login, test_registro_empresa, test_procesos, test_modelado, test_usuarios y test_roles).
  • conftest.py: fixtures de navegador, empresa de prueba, sesión y datos encadenados; datos.py: generadores de datos únicos; pytest.ini y requirements.txt.
  • Backend: postman/ (2 colecciones), jmeter/ (4 planes) y src/test/java (58 clases).

Casos priorizados: se priorizó por riesgo: primero sesión y rutas protegidas (seguridad), luego el modelado (núcleo del producto), el ciclo de vida del proceso y la administración. Las fixtures encadenan los datos (empresa → sesión → rol o proceso → pool → lane), así cada caso crea solo lo que necesita y los casos se pueden correr en cualquier orden.

Preparación y limpieza de datos: la fixture de sesión registra por la interfaz una empresa nueva por ejecución («Empresa E2E <hex>», correos @example.com, contraseña aleatoria con secrets.token_urlsafe), y cada caso usa nombres únicos (unico()). Los scripts ci/levantar-backend-e2e.sh y ci/bajar-backend-e2e.sh vacían la base proyecto_ci_front antes y después. En la API, la colección genera NIT y correos dinámicos y la base proyecto_ci también se vacía.

Identificadores / selectores y estabilidad de scripts:

  • Selectores CSS por formcontrolname y tipo de botón, XPath por el texto de la celda (fila() y celda()) e ids leídos del href de los enlaces, sin depender de posiciones.
  • Esperas explícitas (WebDriverWait con expected_conditions) y tiempo configurable con E2E_TIMEOUT (10 s en local, 20 s en CI); la única pausa es el sondeo de 0,1 s dentro de textos_estables().
  • Escritura con Ctrl+A y Supr para que los formularios de Angular detecten el cambio; textos_estables() espera a que la lista de mensajes de validación deje de cambiar.
  • Un navegador nuevo por caso, ventana fija de 1366×900, captura PNG automática al fallar y ninguna credencial en el código (--tb=short evita imprimirlas).

3. Ejecución

Comandos para ejecutar suites:

  • E2E: pip install -r e2e/requirements.txt; $env:E2E_BASE_URL = "http://<host>:<puerto>"; python -m pytest e2e -v (un archivo: python -m pytest e2e/tests/test_procesos.py -v).
  • E2E en CI: python -m pytest e2e -v --junitxml=e2e/reportes/junit.xml --html=e2e/reportes/reporte.html --self-contained-html.
  • API: newman run postman/Facimus-HU-Flow.postman_collection.json --env-var baseUrl=<url>.
  • Carga: jmeter -n -t jmeter/plan-login.jmx -JBASE_URL=<host> -JPORT=<puerto> -l resultados.jtl -e -o html.
  • Unitarias: ./mvnw clean verify y npx ng test --watch=false --browsers=ChromeHeadlessCI --code-coverage.

Ejecución local y en integración continua (CI): en local, la suite apunta a cualquier instancia con E2E_BASE_URL, con navegador visible o sin ventana. En CI, el job «Pruebas E2E (Selenium)» del workflow CI/CD Front levanta por Tailscale y SSH un backend temporal en beta-back (imagen beta-back:latest, base vacía proyecto_ci_front), arranca en el runner la imagen del front recién publicada en http://localhost:8080 y ejecuta pytest con E2E_HEADLESS=1 y E2E_TIMEOUT=20. Después publica la tabla «Reporte E2E Selenium», un resumen y el artefacto reporte-e2e (HTML, JUnit, capturas y logs), y siempre limpia el entorno.

Configuración y variables requeridas:

  • Suite E2E: E2E_BASE_URL (obligatoria), E2E_HEADLESS y E2E_TIMEOUT.
  • Secretos del CI: TS_OAUTH_CLIENT_ID y TS_OAUTH_SECRET (Tailscale), DEPLOY_SSH_KEY con BACK_KNOWN_HOSTS (SSH), DB_PASSWORD (bases de prueba) y GITHUB_TOKEN (GHCR); JWT_SECRET se genera al azar en cada ejecución (openssl rand -hex 32).
  • Newman: baseUrl; JMeter: BASE_URL y PORT.

Frecuencia de ejecución: en cada pull request a main (si falla, el PR queda en rojo), en cada merge a main (el despliegue solo ocurre si pasa la suite E2E) y a mano desde Actions (workflow_dispatch) sobre cualquier rama, sin desplegar. Unitarias, arquitectura y SonarCloud corren en cada PR y en cada push a main.

5. Mantenimiento y cierre

Criterios de aceptación: 100 % de casos E2E aprobados en el PR (condición para el merge) y en main (condición para desplegar); 0 fallos en Postman (si una aserción falla, el job falla); JMeter informativo, con los umbrales del documento 04; Quality Gate de SonarCloud aprobado; y ningún caso intermitente: si aparece uno, se corrige la espera o el selector, no se reintenta.

Acciones correctivas y responsables:

  • Actualizar los textos esperados del login tras el pulido visual: Samuel Bonilla (PR #42, hecho el 23/11/2026).
  • Corregir el orden, las variables y las aserciones de Facimus-Procesos-API: Samuel Bonilla (propuesto).
  • Casos E2E para mensajes, correlación, procesos compartidos y permisos de estructura: Samuel Bonilla y Samuel Giraldo (propuesto).
  • Agregar el frontend a SonarCloud y umbrales de duración en JMeter: Juan Guillermo Gómez y Andrés Ospina (propuesto).

Mantenimiento de scripts: el patrón Page Object concentra los selectores, así que un cambio de pantalla se corrige en un solo archivo; los tests describen el comportamiento. Si cambian los textos de la interfaz, se actualizan los mensajes esperados (como en el PR #42). Los datos únicos por ejecución evitan depender de limpiezas manuales. Las dependencias tienen rangos acotados (selenium>=4.52,<5 y pytest>=8,<10), Selenium Manager resuelve el chromedriver y los reportes se conservan 14 días como artefactos.

Conclusiones: las pruebas E2E, de API, de carga, unitarias y de arquitectura corren solas en cada cambio y actúan como compuertas del merge y del despliegue. El 23/11/2026 la compuerta E2E detectó que los textos del login habían cambiado sin actualizar las pruebas y bloqueó el despliegue hasta corregirlo. Queda pendiente ampliar los casos E2E a mensajes, correlación y procesos compartidos.
