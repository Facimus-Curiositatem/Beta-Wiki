1. Objetivo y alcance

Objetivo medible de la prueba: comprobar que la API REST, desplegada como contenedor Docker con el perfil prod y PostgreSQL, atiende hasta 50 usuarios concurrentes en los flujos críticos (autenticación, gestión de procesos y roles, y modelado BPMN) con p95 ≤ 1.000 ms, p99 ≤ 1.500 ms, 0 % de errores y APDEX ≥ 0,85 en cada escenario.

Flujos BPMN o endpoints que serán evaluados: cuatro planes JMeter que reproducen flujos reales de uso. Cada usuario virtual registra su propia empresa e inicia sesión antes de operar, de modo que la carga respeta el aislamiento multiempresa.

  • CP-01 Autenticación (plan-login.jmx): POST /api/v1/empresas, POST /api/v1/auth/login, POST /api/v1/auth/refresh y POST /api/v1/auth/logout.
  • CP-02 CRUD de procesos (plan-procesos-crud.jmx): crear, listar, consultar, editar, publicar (PATCH con estado PUBLICADO) y eliminar sobre /api/v1/procesos.
  • CP-03 CRUD de roles (plan-roles-crud.jmx): crear, listar, editar y eliminar sobre /api/v1/roles.
  • CP-04 Modelado BPMN (plan-modelado-bpmn.jmx): crear rol y proceso, listar pools, crear lane, dos actividades y un gateway, conectar dos arcos, editar una actividad, listar actividades y arcos, y consultar el diagrama completo (GET /api/v1/procesos/{id}/diagrama).

Ambiente y características de infraestructura:

  • Sistema bajo prueba: contenedor Docker temporal beta-back-ci en la VM beta-back (Ubuntu 22.04.5 LTS sobre VMware, 4 vCPU Intel Xeon Gold 6240R a 2,40 GHz y 11,6 GiB de RAM), con la imagen ghcr.io/facimus-curiositatem/beta-back:pr-52: Spring Boot 4.1.0, Java 21.0.13 y Tomcat 11.0.22, perfil prod, límite de 768 MB de memoria y heap máximo del 60 % (-XX:MaxRAMPercentage=60).
  • Base de datos: PostgreSQL 18.6 en una VM dedicada de la red de la universidad; base proyecto_ci, que se vacía antes y después de cada corrida (Hibernate ddl-auto=create).
  • Generador de carga: runner ubuntu-latest alojado por GitHub (AWS, us-east-1, 4 procesadores) con Apache JMeter 5.6.3 y 1 GB de heap; llega a la VM por Tailscale.
  • La misma VM aloja el contenedor de producción (beta-back, límite de 1 GB), que siguió en servicio durante la prueba.

2. Escenarios y criterios

Usuarios concurrentes esperados: el equipo fijó como carga objetivo hasta 50 usuarios virtuales simultáneos: 50 en autenticación (todo usuario pasa por el login), 30 en el CRUD de procesos y 20 en el CRUD de roles y en el modelado BPMN.

Patrón de incremento de carga: rampa lineal del Thread Group de JMeter, sin tiempo de espera entre peticiones (think time 0). CP-01 arranca 50 hilos en 10 s (5 hilos/s); CP-02, 30 hilos en 10 s (3 hilos/s); CP-03 y CP-04, 20 hilos en 5 s (4 hilos/s). Cada hilo repite su flujo 5, 3, 5 y 3 veces, respectivamente, así que al terminar la rampa toda la concurrencia queda activa (carga de estrés sostenida). Los planes se ejecutan uno tras otro, no en paralelo.

Duración de cada escenario: medida entre la primera y la última muestra del archivo JTL: CP-01 14,7 s (1.000 peticiones), CP-02 12,9 s (720 peticiones), CP-03 9,0 s (600 peticiones), CP-04 10,6 s (900 peticiones). En total, 3.220 peticiones en unos 47 s de carga efectiva.

Umbrales de aceptación definidos por el equipo:

  • Errores = 0 %: toda petición debe devolver el código esperado (aserciones 200, 201 o 204 en cada sampler).
  • Latencia por escenario: p95 ≤ 1.000 ms y p99 ≤ 1.500 ms (1.500 ms es el umbral de frustración del APDEX de JMeter).
  • APDEX ≥ 0,85 por escenario, con T = 500 ms y F = 1.500 ms (configuración por defecto del dashboard).
  • Throughput: sin mínimo obligatorio; se registra como línea base para comparar versiones.

3. Preparación y ejecución

Herramienta empleada y versión: Apache JMeter 5.6.3 en modo sin interfaz (jmeter -n) con dashboard HTML (-e -o), sobre Java 21 (Temurin) en el runner de GitHub Actions. El script ci/resumen_jmeter.py publica el resumen en la página de la ejecución y el artefacto reporte-jmeter guarda el JTL, el log y el dashboard de cada plan.

Datos de prueba utilizados: datos sintéticos generados en cada iteración con funciones de JMeter (${__threadNum}, ${__RandomString}): empresa, NIT y correo de administrador únicos, contraseña de prueba fija y nombres únicos de roles, procesos, lanes, actividades y gateways. El token, el refresh token y los ids creados (proceso, pool, lane, rol, actividades y gateway) se capturan con JSON Extractor y se envían en las peticiones siguientes con un HTTP Header Manager (Authorization: Bearer). No se usan datos reales.

Configuración del script / enlace: carpeta jmeter/ de Beta-back. Cada plan recibe BASE_URL y PORT como propiedades (${__P(BASE_URL,localhost)}, ${__P(PORT,8080)}) y define un Thread Group con la rampa indicada, aserciones de código de respuesta en cada petición, JSON Extractors y encabezados por petición, sin temporizadores. Se ejecuta en el job «Postman y JMeter (VM beta-back)» de .github/workflows/ci.yml.

Procedimiento de ejecución:

  • Un pull request hacia main dispara el workflow CI/CD Backend: build, JUnit, ArchUnit, SonarCloud y publicación de la imagen :pr-N en GHCR.
  • El job de pruebas de API se conecta a Tailscale, abre SSH a beta-back y levanta el backend temporal con la imagen del PR contra proyecto_ci (ci/levantar-backend-ci.sh).
  • Cuando la API responde 401/403 en /api/v1/procesos, ejecuta las colecciones Postman y luego los cuatro planes: jmeter -n -t jmeter/<plan>.jmx -JBASE_URL=<host> -JPORT=<puerto> -l resultados.jtl -j jmeter.log -e -o html.
  • Publica el resumen en la página de la ejecución y los artefactos reporte-postman y reporte-jmeter (retención de 14 días).
  • Siempre baja el backend temporal y vacía la base (ci/bajar-backend-ci.sh).
  • Para medir recursos, el 23/11/2026 se re-ejecutó el job del PR #52 (intento 2) mientras un script en beta-back registraba cada segundo la CPU y la memoria de los cgroups de Docker y del host. Los resultados de este documento corresponden a esa corrida.

4. Resultados y análisis

Latencia media, p95 y p99: valores del dashboard de JMeter (statistics.json): CP-01 media 293,1 ms, p95 578,9 ms y p99 696,9 ms (máximo 849 ms); CP-02 media 137,4 ms, p95 279,0 ms y p99 303,9 ms (máximo 333 ms); CP-03 media 149,8 ms, p95 302,9 ms y p99 368,0 ms (máximo 410 ms); CP-04 media 130,1 ms, p95 282,9 ms y p99 318,0 ms (máximo 389 ms). Sobre las 3.220 muestras de los cuatro JTL: media 186,0 ms, mediana 114 ms, p95 480 ms y p99 619 ms.

Solicitudes por segundo / throughput: CP-01 67,9 peticiones/s, CP-02 56,0 peticiones/s, CP-03 66,5 peticiones/s, CP-04 85,1 peticiones/s (rendimiento agregado de cada escenario). Por operación, entre 6,8 y 17,7 peticiones/s, según el número de pasos de cada flujo.

Tasa de errores: 0,00 % (0 errores en 3.220 peticiones). Todas las aserciones de código de respuesta pasaron y el log del backend temporal no registra excepciones.

Consumo de CPU y memoria: medido en la VM beta-back con muestreo cada segundo de los cgroups v2 del contenedor de pruebas (límite de 768 MB). En reposo, tras el arranque, el contenedor usaba 260 MB y 0,28 núcleos. El pico de memoria fue 418 MB (54 % del límite) y la CPU de toda la VM llegó a 98,8 % como máximo; no hubo reinicios ni errores por memoria.

  • Postman: CPU media 0,52 núcleos (máx. 1,69, 42 % de los 4 vCPU); memoria media 332 MB (máx. 338 MB).
  • CP-01: CPU media 3,10 núcleos (máx. 3,79, 95 % de los 4 vCPU); memoria media 364 MB (máx. 382 MB).
  • CP-02: CPU media 2,01 núcleos (máx. 2,84, 71 % de los 4 vCPU); memoria media 413 MB (máx. 418 MB).
  • CP-03: CPU media 2,52 núcleos (máx. 3,56, 89 % de los 4 vCPU); memoria media 405 MB (máx. 406 MB).
  • CP-04: CPU media 2,29 núcleos (máx. 3,33, 83 % de los 4 vCPU); memoria media 394 MB (máx. 404 MB).

Cuellos de botella identificados:

  • CPU: en CP-01 el contenedor llegó a 3,79 núcleos (95 % de los 4 vCPU) y la VM completa a 98,8 %: con 50 usuarios simultáneos, el hash BCrypt de registro y login satura la CPU. La memoria no es una restricción (máximo de 418 MB, 54 % del límite).
  • Registro y login (BCrypt): son las operaciones más costosas en los cuatro escenarios, con p95 agregado de 628 ms y 520 ms, frente a 103–150 ms del resto de operaciones. Ambas calculan o verifican un hash BCrypt, un costo de CPU deliberado por seguridad; el registro además crea empresa y administrador en una sola transacción. Con 50 hilos, el registro baja a un APDEX de 0,810, nivel «regular» de la escala (de 0,70 a 0,85).
  • Resto de la API: CRUD y modelado se mantienen entre 97 ms y 119 ms de media, incluido el diagrama completo del proceso; no hay degradación progresiva durante la rampa.
  • Latencia de red: todas las peticiones tienen un piso de unos 90 ms (mínimo observado), incluso un GET simple, y Newman muestra el mismo piso (93 ms). Ese piso corresponde sobre todo al trayecto entre el runner de GitHub (AWS, us-east-1, EE. UU.) y la VM a través de Tailscale, no al procesamiento del servidor.

5. Cierre

Comparación con criterios de aceptación: los cuatro escenarios cumplen todos los umbrales (tabla «Resultados»): p95 máximo 578,9 ms (CP-01) frente a 1.000 ms; p99 máximo 696,9 ms frente a 1.500 ms; 0,00 % de errores; y APDEX de 0,932 (CP-01), 1,000 (CP-02), 1,000 (CP-03), 1,000 (CP-04), todos ≥ 0,85. El margen más estrecho está en la autenticación, por el costo de BCrypt.

Acciones de mejora:

  • Convertir los umbrales en aserciones de duración (Duration Assertion) para que el job falle si se superan, como ya ocurre con las aserciones de Postman.
  • Incluir en el CI la medición de recursos (Spring Boot Actuator con Micrometer, o el muestreo de cgroups usado en este documento).
  • Agregar un escenario de resistencia (≥ 10 min) y uno de picos para detectar fugas de memoria y la saturación del pool de conexiones a PostgreSQL.
  • Generar la carga desde la red de la universidad (por ejemplo, desde la VM beta-front) para separar la latencia de red del tiempo de servidor.
  • Para atender más de 50 usuarios simultáneos, asignar más vCPU o réplicas al backend, porque la autenticación ya lleva la CPU cerca del 100 %; no reducir el factor de costo de BCrypt.
